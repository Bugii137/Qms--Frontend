# React + Vite

This template provides a minimal setup to get React working in Vite with HMR and some Oxlint rules.

Currently, two official plugins are available:

- [@vitejs/plugin-react](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react) uses [Oxc](https://oxc.rs)
- [@vitejs/plugin-react-swc](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react-swc) uses [SWC](https://swc.rs/)

## React Compiler

The React Compiler is not enabled on this template because of its impact on dev & build performances. To add it, see [this documentation](https://react.dev/learn/react-compiler/installation).

## Expanding the Oxlint configuration

If you are developing a production application, we recommend using TypeScript with type-aware lint rules enabled. Check out the [TS template](https://github.com/vitejs/vite/tree/main/packages/create-vite/template-react-ts) for information on how to integrate TypeScript and Oxlint's TypeScript related rules in your project.

## CRUD and record retention

The QMS exposes create, read, update, and delete/archive actions through role-scoped API routes and the corresponding management screens. System admins manage accounts and institutions; institution admins manage services, staff assignments, and appointments; clients manage their own bookings; notifications are generated by the system and managed by their recipient.

Delete actions preserve operational history: accounts are deactivated, institutions suspended, services deactivated, staff assignments marked inactive, and appointments cancelled. Notifications can be permanently deleted by their owner. Authenticated API routes reject inactive accounts.

## Backend email delivery

Copy `backend/.env.example` to `backend/.env`, then set the SMTP host, port, username, password, and a sender address verified with your email provider. For Gmail, use a Google app password rather than the account password. Set `MAIL_FROM_NAME` for the sender display name and `CLIENT_URL` to the frontend URL used in password-reset links. Keep SMTP credentials private. The development server watches `.env` and restarts after changes; restart the production backend after changing its environment.

From `backend/`, run `npm run email:verify` to check the SMTP connection and credentials. This verifies the transport but does not send a test message. Signup, profile-change, password-change, password-reset, institution-status, staff, and maintenance emails are sent by the backend. Client signup shows whether SMTP accepted the welcome email and allows an authenticated retry; institution approval reports whether its email notification was accepted. An SMTP acceptance confirms handoff to the provider, not inbox placement, so check spam/junk if a message is missing. A mail-provider failure is logged and reported where the flow can safely expose delivery status; it does not undo a successful account or password change. Forgot-password responses remain generic to avoid revealing whether an email address has an account.

Signup currently sends a welcome/application email but does not require email verification. Password reset uses a single-use, expiring email link; signup verification codes are not implemented.

Appointment request confirmations, approvals, declines, institution-initiated reschedules, cancellations, and completions can notify clients by email and in-app. Clients can manage these event and channel preferences in Profile & Settings; all are enabled by default for existing and new accounts.
